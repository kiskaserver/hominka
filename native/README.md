# native — свій оверлей поверх гри (C++)

Це те, чого не вміє ні безрамковий режим, ні міст у RTSS: показати **справжній**
чат — з аватарками й емоутами — поверх гри у виключному повноекранному режимі.
Спосіб той самий, яким працюють OBS Game Capture, Discord і Steam: своя
бібліотека всередині процесу гри перехоплює показ кадру й домальовує поверх
нього.

Робиться у два кроки. **Цей каталог — крок 1.**

## Крок 1 (готово): каркас і доказ, що кадр наш

- `injector/injector.cpp` → `injector.exe` — кладе `overlay.dll` у процес гри
  (`VirtualAllocEx` + `WriteProcessMemory` + `CreateRemoteThread(LoadLibraryW)`).
  Розрядність цілі визначає `IsWow64Process2`; у 32-бітну гру йде x86-інжектор, у
  64-бітну — x64.
- `overlay/` → `overlay.dll` — перехоплює `IDXGISwapChain::Present` (DX11)
  підміною одного запису у vtable (`vtable_hook.h`) і малює тестовий прямокутник
  (`overlay_dx11.h`, `shaders.cpp`). Прямокутник — і є доказ: його видно поверх
  кадру гри, у її ж свопчейні.
- `common/guard.h` — **тверда відмова** інжектити у змагальні ігри з античитом
  (Valorant, CS2, Rust, Apex, EFT та ін.) і за наявністю самих античитів серед
  модулів процесу. Перевіряється ПЕРШОЮ, до будь-яких дій із процесом.
- `common/log.h` — журнал у `%TEMP%\hominka-overlay.log`: усередині чужого
  процесу більше сказати нікуди.
- `testhost/testhost.cpp` — крихітна гра-макет на DX11 для перевірки (у випуск не
  входить).

Що вже перевірено на живому прогоні: інʼєкція проходить, `Present`
перехоплюється («перший перехоплений Present — кадр наш» у журналі), фіолетовий
прямокутник Hominka зʼявляється поверх кадру тестового хоста; guard відмовляє
для `valorant.exe` з кодом 3 ще до пошуку DLL.

## Крок 2 (готово): справжній чат через спільну память

DLL читає буфер зі спільної памʼяті, заливає в текстуру й малює поверх кадру гри
з альфою. Зроблено для всіх шляхів показу кадру: `Present` (DX11/DXGI),
`EndScene` (DX9), черга команд (DX12), `wglSwapBuffers` (OpenGL) і
`vkQueuePresentKHR` (Vulkan), з повним збереженням і відновленням стану рендера.

**Хто кладе кадр — змінилося.** Спершу це робив Python: показував чат у
браузері за межами екрана, знімав із нього картинку (`QWebEngineView.grab()`),
рахував CRC по всьому кадру, щоб зрозуміти, чи він змінився, і перекладав байти
в спільну память. Тепер кадр кладе туди сам нативний рендер
(`render/frame_writer.h`): чат уже намальовано на відеокарті, лишається забрати
його звідти. CRC не потрібен — ми й так знаємо, чи малювали. Читання з
відеокарти робиться ЛИШЕ поки інжект увімкнено.

## Як користуватися injector.exe

```
injector-x64.exe --exe game.exe            вкласти overlay.dll (поруч) у гру за іменем
injector-x64.exe --pid 1234                те саме за PID
injector-x64.exe --exe game.exe --dll D:\...\overlay.dll   свій шлях до DLL
injector-x64.exe --exe game.exe --check    лише перевірити, чи можна (не чіпає процес, DLL не треба)
```

Коди виходу (щоб програма могла сказати щось конкретніше за «не вдалося»):
`0` готово · `1` помилка в аргументах / немає overlay.dll · `2` процес не
знайдено · `3` **відмова: античит** · `4` не та розрядність DLL · `5` інша
помилка інʼєкції. Розрядність DLL і цілі мусять збігатися: у 64-бітну гру —
`injector-x64` + `overlay-x64.dll`, у 32-бітну — `-x86`.

## render/ — нативний рендер чату (litehtml + Direct2D)

Окремий напрям: перенести САМЕ МАЛЮВАННЯ чату з QWebEngine у C++. Сьогодні
картинку чату робить Chromium, а щоб показати її поверх гри, програма робить
коло GPU→CPU→GPU: `QWidget.grab()` → CRC32 по всьому кадру → спільна память →
`UpdateSubresource`. Звідси й обмеження в ~8 кадрів/с, і пауза грабера під час
перетягування вікна.

litehtml замість Chromium узято заради ТЕМ: сторінка чату лишається HTML+CSS, а
отже свій CSS користувача (`hominka/cssui/`) і всі написані теми працюють далі.
Малює Direct2D + DirectWrite — вони є в кожній Windows, добре кладуть кирилицю
з емодзі й пишуть прямо в ту саму текстуру, яку показує DirectComposition.

- `page_assets.h` — дзеркало `hominka/feed/page.py`: базові стилі, значки
  площадок, текстові плашки. Класи й data-атрибути — публічна домовленість,
  розійдуться тут — зламаються чужі теми.
- `chat_doc.{h,cpp}` — складання розмітки ОДНОГО повідомлення (порт `PARTS`,
  `body()`, правил емоутів і підсвітки «@ніка»).
- `container_d2d.{h,cpp}` — `litehtml::document_container` на Direct2D.
- `imgcache.{h,cpp}` — картинки: WIC (PNG/JPEG/GIF, зі складанням кадрів
  анімації), libwebp (емоути 7TV/BTTV, зокрема анімовані),
  nanosvg (значки). Мережі тут немає — байти шле Python.
- `feed.{h,cpp}` — стрічка: кеш намальованих рядків, складання кадру, поява.
- `chrome.{h,cpp}` — рамка вікна на Dear ImGui: смужка перетягування, замок,
  A−/A+, повзунки прозорості, шестерня, куточок для розтягування.
- `ipc.{h,cpp}` — канал до Hominka (кадри «довжина + JSON + вкладення»).
- `../common/dcomp_window.h` — вікно D3D11 + DirectComposition + Direct2D,
  спільне зі старим `dcomp_overlay.exe`.
- `frame_writer.h` — кадр у спільну память для overlay.dll (лише коли інжект
  увімкнено).
- `main.cpp` — три режими: `--selftest`, `--run`, `--probe`.

Перевірка (саме вона й ділить «працює» від «схоже»):

```powershell
python native/render/make_samples.py native/render/samples.json
native/dist/hominka-render-x64.exe --selftest native/render/samples.json native/render/out.png
python native/render/reference_shot.py native/render/ref.png   # той самий чат у QWebEngine
python native/render/compare.py native/render/ref.png native/render/out.png native/render/side.png
```

`side.png` кладе браузер і нативний рендер поруч. Станом на зараз розбіжність —
0.6% висоти стрічки (9 px на 29 повідомленнях).
Решта збігається: кольори, накреслення, плашки, емоути, підсвітка згадок, тінь
тексту (зокрема `text-shadow: none` на плашках) і вирівнювання по базовій лінії.

Частини CSS litehtml не знає. Закриваємо їх двома різними способами, і вибір
між ними не довільний.

**Самим контейнером** — коли рушієві про властивість знати нічого не треба, бо
вся вона зводиться до того, як лягає фарба. Тут CSS переписується ТЕКСТОМ, і
саме тому поруч стоїть окрема перевірка (`css_smoke.py`): помилка в такому
переписуванні не лишається локальною. Одна загублена дужка — і відкрита
«rgba(» проковтне все, що йде далі; тема не падає, просто половина її правил
тихо не діє, а очима це не побачити. Один раз так і вийшло: закривальну дужку
для `drop-shadow(…)` шукали першою-ліпшою, а нею виявлялася дужка від `rgba()`
всередині.

- `text-shadow` — проводимо разом зі шрифтом, через `text-emphasis-style`
  (`adapt_css` у `cssbits.cpp` — спільно для обох систем). Працює по-елементно, тож
  `text-shadow: none` на плашці справді її не тінить.
- `filter: drop-shadow(…)` — переписуємо в `text-shadow` там-таки.
- перенос довгих посилань — `ContainerD2D::split_text`. litehtml сам рве рядок
  лише по пробілах, тож посилання на пів екрана просто виїжджало за край.
  Дозволяємо розрив після `/?&=#-_`, а суцільний шматок від 28 знаків ріжемо
  силоміць. Те саме повідомлення в браузері займає 108 px, у нас — 130 px і
  нічого не обрізано (раніше було 103 px і хвіст за кадром).

**Латкою до самого litehtml** — коли властивість міняє РОЗКЛАДКУ або порядок
малювання, і контейнер тут безсилий. Латки лежать у `patches/` і накочуються
`thirdparty.sh` за іменами, **порядок значущий**: пізніші спираються на рядки,
які додали попередні (`03-box-shadow` — на `02-opacity`). Тому не перейменовуй
їх і не міняй місцями.

| латка | що дає | як перевірено |
|---|---|---|
| `01-…-vertical-align-length` | `vertical-align: <довжина>` | висоти `0` / `-1.5em` / `+1.5em` при `height: 3em` — 65 / 60 / 95, точно як у браузері |
| `02-…-opacity` | `opacity` | яскравість при `1.00` / `0.50` / `0.25` — 255 / 136 / 77 |
| `03-…-box-shadow` | `box-shadow` | мʼяка (`0 3px 8px black`), тверда (`4px 4px 0 #f0f`) і сяйво на плашці (`0 0 6px #0ff`) |
| `04-…-transform` | `transform` | `scale(1.6)`, `translateX(30px)`, `rotate(-8deg)` |

Про `01`: спершу тут був обхід (переклад у `position:relative; top:…`), але
відносне зміщення не збільшує висоту рядка — високий емоут, опущений униз,
залазив на сусідній.

Про `02` і `04`: обидві впираються в одне й те саме. Елемент малюється НЕ за
один раз — фон іде проходом `draw_block`, вміст наступним проходом того ж
батька. Під шар прозорості (чи під матрицю) мають потрапити обидва, інакше
накриє лише половину. Тому в `render_item.cpp` зʼявився `draw_opacity_group`:
він малює елемент разом із нащадками в одному місці, а решті проходів чіпати
його вдруге забороняє (`process = false`).

Про `03`: значення тіні несемо в контейнер РЯДКОМ, як його написали. Рушієві
розбирати «10px 4px 8px rgba(…)» ні до чого, а той, хто малює, однаково має
знати і колір, і розмиття. Так само зроблено з `transform`. Обмеження: тінь не
малюється для `display: inline` — litehtml там не проходить через
`draw_background`.

### Робочий режим

`--run <pid Hominka>` піднімає вікно оверлея й чекає на повідомлення каналом
`\\.\pipe\Hominka-<pid>`. Кадру ззовні більше не приходить: рендер малює чат
сам із подій («нове повідомлення», «прибери це», «ось свій CSS», «ось байти
емоута»). Ані грабера, ані спільної памʼяті на цьому шляху немає.

Мережі в рендері теж немає принципово: емоути й значки качає Python
(`hominka/imagefetch.py`) і шле байтами. Доки картинка їде, рядок показує код
емоута — рівно як чат виглядав, доки емоутів не було; коли байти приїжджають,
рядок перемальовується вже з картинкою.

### Анімовані емоути

Тут була пряма суперечність із головною ідеєю: рядок малюється РАЗ І НАЗАВЖДИ,
а анімований емоут мусить мінятися далі. Розвʼязано тим, що емоут у картинку
рядка не запікається взагалі — на його місці лишається **дірка**
(`ContainerD2D::set_record_sprites`), а кадри кладе поверх уже сама стрічка,
щоразу свій. Робота на кадр виходить пропорційна кількості емоутів У ВІКНІ, а
не розміру стрічки: самі рядки лежать готовими текстурами й не чіпаються.

Чому саме дірка, а не «запекти перший кадр і малювати наступні поверх»: емоути
напівпрозорі по краях, і крізь наступний кадр просвічував би перший.

Частота — не 60 к/с. `Feed::draw` рахує, коли найближчий ВИДИМИЙ емоут
перемкне кадр, і кладе цей момент у `next_anim_ms_`; `dirty()` до нього просто
не спрацьовує. Емоут на 100 мс дає рівно 10 перемальовувань на секунду
(перевірено: `anim_smoke.py` бачить 20 кадрів за дві секунди). Немає видимих
анімованих емоутів — стрічка засинає намертво, як і до всієї цієї роботи.

**GIF — це не послідовність картинок.** Кадри в ньому лежать латками: шматок зі
своїм зсувом, який накладається на попередній стан, ще й із правилом, що
робити перед наступним (лишити, витерти прямокутник, вернути як було). WIC
віддає їх саме так, як вони лежать, тож збираємо кадри самі (`decode_wic`).
Хто цього не робить, отримує емоут, який стрибає й обрізається. У BTTV
анімовані емоути приходять саме GIF-ом, тож випадок не теоретичний.

WebP (7TV, FFZ) простіший: `WebPAnimDecoder` з libwebp сам віддає складені
кадри. Питати в 7TV `.gif` замість `.webp` не треба — WebP і компактніший, і
розбирається без WIC узагалі.

**Памʼять обмежена, і в двох місцях одразу.** Розібрані кадри — це BGRA без
стиснення: емоут 128×128 на 24 кадри важить 1.5 МБ, і сорок таких дають 60 МБ
на рівному місці. Тому:

| межа | скільки | навіщо |
|---|---|---|
| `ANIM_MAX_BYTES` | 64 МБ | стеля на всі розібрані анімації разом |
| `ANIM_MAX_COUNT` | 64 шт. | і на їх кількість |
| `ANIM_MAX_IMAGE_BYTES` | 8 МБ | емоут-монстр лишається НЕРУХОМИМ: краще статична картинка, ніж 60 МБ на один значок |

Вигнання — найдавніше питані першими (`ImageCache::gc_animated`), раз на
секунду й після кожної нової картинки. Не викидаємо ніколи те, на що
посилаються ВИДИМІ рядки: емоут, який зник просто під час показу, гірший за
перевищену межу. Саме тому множина закріплених мала — видно десяток рядків, а
не всі вісімдесят.

Друга половина межі — текстури на відеокарті. Кожен намальований кадр стає ще
й `ID2D1Bitmap`, і сорок емоутів по двадцять чотири кадри — це тисяча текстур.
`Feed::trim_anim()` викидає текстури тих емоутів, яких зараз не видно (в
навантажувальній перевірці це дало −22 МБ).

Під навмисно нездоровим потоком — 60 різних емоутів 128×128 на 24 кадри, тобто
94 МБ анімацій — процес тримається на 134 МБ, кеш стоїть на 63 МБ і не росте.

Анімацію можна вимкнути зовсім (`Feed::set_animate(false)`) — тоді від кожного
емоута лишається перший кадр. Самоперевірка так і робить: інакше PNG виходив
би різним щоразу.

Вмикається ключем `renderer` у `config.json`:

```json
{"renderer": "native"}
```

Типове значення — `"web"`, тобто все як було (грабер кадру з браузера). Так
новий шлях можна ввімкнути й порівняти зі старим на тій самій машині.

Три перевірки живого шляху. Перші дві роблять знімок того, що рендер справді
показує у вікні (звичайний скриншот його не побачить — вікно приховане від
захоплення). Третя дивиться на перегляд у редакторі CSS, і не лише «чи є
кадр»: вона рахує кадри за дві секунди спокою. Їх має бути нуль — намальований
рядок не перемальовується, у цьому весь виграш. Колись тут було 60 к/с на
нерухомій картинці, бо `Feed::dirty()` рахував і рядки, що виїхали за край.

```powershell
python native/render/ipc_smoke.py     # канал і рендер окремо  → live.png
python native/render/app_smoke.py     # уся програма цілком    → app.png
python native/render/preview_smoke.py # перегляд у редакторі   → preview.png
python native/render/css_smoke.py     # розбір CSS чужих тем
python native/render/anim_smoke.py    # анімовані емоути й межа кеша

Linux-перевірки йдуть у контейнері (див. розділ нижче): `linux_smoke.py`
(канал, вікно, малювання), `pyclient_smoke.py` (справжній клієнт Python),
`chrome_linux_smoke.py` (рамка), `preview_linux_smoke.py` (предпросмотр),
`app_linux_smoke.py` (уся програма).
```

### Вікно чату замість браузера

Коли `renderer` = `"native"` І задано канал Twitch/Kick, вікном чату СТАЄ вікно
рендера, а Qt-вікно ховається й лишається лише господарем панелі налаштувань.
Chromium при цьому не запускається взагалі: `QWebEngineView` створюється ліниво
(`Overlay._ensure_web`), і в режимі стрічки цього не стається жодного разу.
Пошук власного ефіру на YouTube теж переїхав на звичайний запит
(`hominka/probelight.py`) — інакше саме він піднімав браузер через чотири
секунди після старту.

Рамку малює ImGui поверх чату й показує ЛИШЕ коли миша над вікном: постійна
смужка поверх гри — шум, а не зручність. Поки миші немає (або вікно замкнене),
воно клік-крізь і не заважає ані грі, ані робочому столу.

Налаштувань рендер не зберігає: він каже Hominka «людина покрутила ось це», а
пише їх у `config.json` вона. Так не буває двох правд і не треба вирішувати,
чиє значення новіше.

Заміряно на цій машині (`app_smoke.py`, ті самі 29 повідомлень):

| | памʼять Hominka | процесів QtWebEngine | процесів рендера |
|---|---|---|---|
| `renderer: "web"` | 212–222 МБ | 4–5 | 0 |
| `renderer: "native"` | 97–106 МБ | **0** | 1 (~70 МБ) |

### Чат усередині гри

Шляхів показати чат поверх гри два, і живить їх ОДИН рендер:

- **вікно DirectComposition** — окреме вікно поверх гри, у гру нічого не
  вкладається. Працює всюди, безпечно для античитів;
- **інжект** — `overlay.dll` усередині процесу гри домальовує чат прямо в її
  кадр. Потрібен для ексклюзивного повноекранного, але це вкладання в чужий
  процес: лише для одиночних ігор і з жорсткою відмовою там, де є античит.

Перевірка інжект-шляху на іграх-макетах (кожна перевіряє свій API):

```powershell
python native/render/inject_smoke.py dx11
python native/render/inject_smoke.py dx12
python native/render/inject_smoke.py gl
python native/render/inject_smoke.py vk
```

У журналі має бути рядок виду
`overlay(dx11): кадр — enabled=1 target=<pid> ми=<pid> розмір=430x560` — саме
він означає, що DLL прочитала той кадр, який поклав рендер.

Розкладку чату в грі рахує сам рендер: де й якого розміру його вікно стоїть на
СВОЄМУ моніторі, там і такого ж розміру чат у кадрі гри
(`DCompWindow::monitor_fraction`). Раніше це рахував Python за Qt-вікном.

**Чого більше немає.** Разом із грабером пішла можливість показувати в грі
ЧУЖУ сторінку: рендер малює стрічку, а не довільний сайт. Стосується це одного
випадку — коли чат відкрито сторінкою YouTube (`youtube.com/live_chat`) замість
власного читача. Чат сайту цього більше не потребує: у нього тепер є свій читач
(`hominka/chat_site.py`), і він приходить у стрічку нарівні з Twitch, Kick та
YouTube — а отже працює і в грі, і в нативному вікні, і без браузера взагалі.

### Перегляд у редакторі CSS

`--preview <pid>` — окремий процес БЕЗ вікна: малює стрічку в память і шле
пікселі назад Hominka, яка показує їх звичайним QLabel
(`hominka/cssui/editor.py`). Раніше там стояв другий браузер, і він показував
не те, що побачить глядач: підтримку CSS у Chromium і в litehtml ніхто не
звіряв. Тепер перегляд — це буквально кадр із того самого рушія.

Канал у нього свій (`Hominka-<pid>-preview`), тож із вікном оверлея вони не
перетинаються ніде: предпросмотр не може ані підмінити його, ані завалити.

Чого рушій не вміє (`filter`, `backdrop-filter`, `animation`, `grid`…) —
зібрано в одному місці, `hominka/cssui/limits.py`. За цим списком і попереджає
редактор, і будується вкладка «Що не працює». Два списки неминуче розійшлися б.
Коли чергову властивість доробляємо, її звідти прибираємо — список має меншати.

Два з них не полагодити в принципі, і краще про це знати:
`backdrop-filter` вимагає пікселів ЗА оверлеєм, а це кадр гри, який DComp
складає вже після нас; `animation` і `transition` суперечать самій конструкції
(намальований рядок більше не перемальовується — на цьому й тримається виграш).

Три випадки ми не ігноруємо, а виконуємо, бо вони найчастіші:

| у CSS | що робимо |
|---|---|
| `filter: drop-shadow(…)` | перекладаємо в `text-shadow` (`adapt_css`) |
| `.m { animation: none }` | вимикаємо нативну появу рядка |
| `#list { flex-direction: column-reverse }` | новіші рядки згори |

Ще дві команди на випадок збою:

```powershell
native/dist/hominka-render-x64.exe --probe        # чи жива зв'язка litehtml+D2D
native/dist/hominka-render.debug.exe --probe      # те саме, але з символами
```

Відладочний бінар при збої друкує ланцюжок викликів зі зсувами; `addr2line -e
hominka-render.debug.exe <адреса>` перетворює їх на «файл:рядок».

**Обережно з рівнем оптимізації litehtml.** На `-O3` (типовий `Release` у
CMake) GCC 12 під mingw збирає його так, що розбір документа псує память і
`createFromString` падає в `memcpy`. Тому в `thirdparty.sh` стоїть `-O2`
(`RelWithDebInfo`). Міняючи версію litehtml чи компілятора — перевір `--probe`.

### Linux: другий контейнер

Рендер чату збирається і під Linux. Малює те саме й тим самим litehtml, а от
все, що нижче за розкладку, там інше — під Windows це один DirectWrite, поза
ним доводиться складати з трьох частин:

| що робить | Windows | Linux |
|---|---|---|
| заливки, скруглення, градієнти, перетворення, шари | Direct2D | Blend2D |
| гліфи, зокрема кольорові емодзі | DirectWrite | FreeType |
| пошук шрифту й запасного шрифту під символ | DirectWrite | fontconfig |
| PNG/JPEG/GIF | WIC | stb_image |
| WebP, SVG | libwebp, nanosvg | ті самі |

**Що навмисно спільне.** Розбір CSS (`cssbits.{h,cpp}`) — тіні, кольори,
перетворення, переноси довгих посилань — один на обидві системи, і стрічка
(`feed.{h,cpp}`) теж одна. Мати дві копії стрічки означало б, що одного дня
вони розійдуться тихо, у поведінці. Тому від системи стрічці потрібні лише
шість дій (`feedgfx.h`): зробити полотно, почати й закінчити на ньому
малювання, узяти растр, зробити растр із пікселів, покласти растр із альфою.
Латки до litehtml — теж ті самі й у тому самому порядку: інакше поїхала б
розкладка.

**Чого немає й це відомо.** Складання (shaping) і двонапрямленого письма:
рядок іде символ за символом. Для латиниці, кирилиці, емодзі й CJK цього
досить, арабська й гінді будуть неправильні. Кернінг теж не застосовується.

**Підбір запасного шрифту перевірено на двох випадках**, і другий ледь не
загубився. Кольорові емодзі: fontconfig упорядковує за своєю мірою схожості й
для смайла цілком може поставити першим ЧОРНО-БІЛИЙ символьний шрифт — цей
символ є і в ньому. Тому шукаємо у два заходи: спершу серед тих, у кого
стоїть `FC_COLOR`, і лише потім серед решти. Другий випадок — CJK: там
кольорових шрифтів не буває, і працює звичайний прохід. Обидва намальовані й
звірені з Windows.

Через це на самій машині користувача мають бути шрифти: щось на кшталт
`fonts-noto-core` (основний текст), `fonts-noto-color-emoji` (емодзі) і
CJK-набір, якщо в чат пишуть ієрогліфами. Немає шрифту — символ стане
порожньою плиткою, як і в будь-якій іншій програмі; програма від цього не
падає.

**Шрифт відрізняється, і це видно.** «Segoe UI» поза Windows немає, а
fontconfig не вміє відповідати «нема такого» — він мовчки дає найкраще з
наявного. Через це рядки виходили ширшими й переносилися раніше. Тепер
питаємо, чи це САМЕ та родина, і якщо ні — беремо заміну зі списку. Заміряно
на тих самих 29 зразках (висота полотна проти 1412 px на Windows):

| шрифт | висота | різниця |
|---|---|---|
| DejaVu Sans (типовий у Debian) | 1682 | +19.1% |
| Liberation Sans | 1547 | +9.6% |
| **Noto Sans** (наш вибір) | **1520** | **+7.6%** |

Решта 7.6% — це вже різниця самих накреслень, а не помилка підбору. Точної
рівності не буде, доки шрифт не той самий; тема від цього не ламається, але
довгий рядок може перенестися на слово раніше.

Збирається так:

```powershell
docker build -t hominka-native native                        # база (обидві системи)
docker build -f native\Dockerfile.linux -t hominka-lin native  # сам рендер
docker run --rm hominka-lin /out/hominka-render-linux --probe
```

`Dockerfile.linux` береться від готового `hominka-native`, тож пересбірка —
це рівно наші файли, секунди. Самоперевірка та сама, що й під Windows:

```powershell
docker run --rm -v ... /out/hominka-render-linux --selftest samples.json out.png
```

#### Вікно й канал

`--run <pid Hominka>` піднімає вікно оверлея й чекає команд — те саме, що й під
Windows, і тими самими кадрами. Змінилося лише, ЧИМ носяться байти:

|  | Windows | Linux |
|---|---|---|
| канал | іменований канал `\\.\pipe\Hominka-<pid>` | сокет `$XDG_RUNTIME_DIR/hominka-<pid>.sock` |
| вікно поверх усього | `WS_EX_TOPMOST` + DirectComposition | override-redirect + `_NET_WM_STATE_ABOVE` |
| напівпрозорість | `WS_EX_NOREDIRECTIONBITMAP` + DComp | 32-бітний ARGB-візуал |
| клік наскрізь | `WS_EX_TRANSPARENT` | порожня ВХІДНА область (XShape) |
| перетягування | смужка ImGui | рахуємо самі (override-redirect) |

Каналів так само два. На Linux замка на дескриптор немає, тобто причина, яка
змусила розділити їх під Windows, тут не діє — але домовленість має бути ОДНА,
інакше Python довелося б писати двічі.

Сокет кладемо в `XDG_RUNTIME_DIR` (тека саме цього користувача й сеансу —
найближче до `Local\` у Windows), права `0600`. Чат — приватне листування, і
сокет у `/tmp` не має бути відкритий усій машині.

**Дві речі відрізняються, і мовчати про них не можна.**

*Перше: від запису чат НЕ сховати.* Під Windows це один виклик
(`WDA_EXCLUDEFROMCAPTURE`), і завдяки йому чат видно стримеру, але не глядачам.
В X11 такої речі не існує взагалі: будь-яка програма, що знімає екран, зніме й
оверлей. Тому на Linux чат у записі БУДЕ видно — це треба сказати людині, а не
виявити на стрімі.

*Друге: прозорість вимагає композитора.* ARGB-візуал сам по собі нічого не
змішує; потрібен запущений composite manager (picom, KWin, Mutter). Без нього
замість прозорого тла буде чорне. Це властивість системи, а не наша поломка.

#### Python-сторона

`hominka/nativerender.py` — той самий код на обох системах. Різниться рівно
транспорт: `_channel()` дає ім'я каналу, `_connect()` його відкриває, а решта
(черга, потік-писар, розбір подій) не знає, з чим має справу. Позиція вікна
поза Windows їде тим самим кадром `config`, що й розмір: `SetWindowPos` там
нема чим замінити, бо вікно override-redirect ставить себе саме.

Заразом довелося зробити імпортованим `hominka/inject.py`: `from ctypes import
wintypes` поза Windows кидає помилку на самому імпорті, тож модуль не
завантажився б узагалі. Теку з нативними частинами він тепер шукає за маркером,
який на цій системі справді існує (`hominka-render-linux` замість
`injector-x64.exe`).

Перевірка окрема від `linux_smoke.py`, і це не дублювання. Та говорить із
рендером «сама», складаючи кадри руками; ця запускає СПРАВЖНІЙ клієнт — з його
чергою, потоком-писарем і розбором подій:

```powershell
docker build -f native\Dockerfile.linux -t hominka-lin .   # з КОРЕНЯ chat-overlay
docker run --rm hominka-lin sh -c "Xvfb :99 -screen 0 1280x720x24 & sleep 2; \
    DISPLAY=:99 python3 /src/render/pyclient_smoke.py"
```

Зворотний канал перевіряється перетягуванням: `xdotool` підробляє мишу, і ми
чекаємо на подію `geometry`. Прийшло п'ять подій, остання — `x=100 y=70`, тобто
рівно вікно (40,40) плюс зсув (+60,+30). Так проходить увесь шлях: подія X →
наш цикл → сокет → клієнт.

По дорозі знайшлася мертва домовленість. У `ipc.h` значився кадр `need`
(«бракує картинки»), і Linux-цикл його слав. Виявилося, що під Windows такого
кадру не шле ніхто, а в Python немає слухача: емоути й значки Hominka качає
наперед сама (`hominka/imagefetch.py`). Кадр прибрано з обох місць — розходження
між системами гірше за відсутню можливість.

#### Сама програма

Hominka на Linux стартує й малює чат. Тримали її три речі, і всі три — дрібні
порівняно з тим, як виглядали:

1. `from ctypes import wintypes` на рівні модуля в `overlay.py`, `winapi.py` і
   `fullscreen.py`. Поза Windows цей імпорт кидає помилку одразу, тож модуль не
   завантажувався взагалі — а все, що ним користується, і так було під
   `if IS_WINDOWS`. Достатньо було guard'а.
2. `class _MONITORINFO(ctypes.Structure)` у `fullscreen.py`: тіло класу
   виконується ПРИ ІМПОРТІ, тож самого guard'а на імпорт було мало.
3. `if self.renderer != "native" or not IS_WINDOWS: return` в
   `Overlay._start_native`. Умова була чесною, доки рендера під Linux не
   існувало; тепер він існує.

Решта `winapi.py` виявилася вже написаною з Linux у голові: `set_click_through`
там має гілку через прапорець Qt, `exclude_from_capture` чесно повертає false, а
в `hominka/x11.py` лежать прохання до композитора (`_NET_WM_BYPASS_COMPOSITOR`,
`_NET_WM_STATE_ABOVE`).

Заразом виправлено місце для даних: у зібраній програмі поза Windows
`LOCALAPPDATA` немає, і `config.json` ліг би в `~/Hominka`. Тепер це
`$XDG_CONFIG_HOME/hominka`, а без змінної — `~/.config/hominka`.

Перевірка (`app_linux_smoke.py`) дивиться на чотири речі, і четверта окремо не
випадково:

```
програма жива через 8 с: так
процес рендера піднявся: так
вікон Hominka на екрані: 3
   0x400002 "Hominka chat overlay"  430x400+60+60
   0x200007 "Hominka"               430x400+60+60
рендер піднятий програмою: так
знімок чату від програми: є (45415 байтів)
пікселів нашого тла у знімку: 62517
```

Перші три можуть пройти й тоді, коли звʼязок між програмою та рендером
розірваний: процеси є, вікна є, а повідомлення нікуди не йдуть. Тому четвертим
заходом програма піднімається в тому ж процесі, події чату кладуться тим самим
шляхом, яким їх кладе Twitch, і в рендера просять знімок — а в ньому рахуються
пікселі прикметного тла.

**Що вже є, крім рендера.** Рамка вікна (замок, A−/A+, прозорість, шестерня —
намальована Blend2D, бо бекенда ImGui для нього довелося б писати з
растеризатора трикутників), предпросмотр для редактора CSS і упакований
AppImage — див. `linux/README.md`. У ньому лежить і сам рендер, зібраний на тій
самій Ubuntu 22.04, що й програма: інакше поламала б glibc.

**Чого немає.** Кадру ВСЕРЕДИНІ гри: `overlay.dll` — річ віконна, і той шлях
вимагав би окремого шару Vulkan/GL. Глобальної гарячої клавіші теж немає, тож
знятий замок доводиться вимикати з панелі налаштувань.

Залежність, яку варто памʼятати: `PySide6` цілком, а не `-Essentials`. Чат Kick
працює через `QtWebSockets`, а це Add-on.

Перевірка — одна, але дивиться на все одразу:

```powershell
docker run --rm hominka-lin sh -c "Xvfb :99 -screen 0 1280x720x24 & sleep 2; \
    DISPLAY=:99 python3 /src/render/linux_smoke.py"
```

Вона піднімає рендер, під'єднується до сокета, шле повідомлення, просить
знімок полотна — і, найголовніше, ЗНІМАЄ КОРІНЬ X через `xwd` і рахує на ньому
пікселі свого прикметного кольору. Без цього останнього кроку вікно могло б
бути створене й показане, а на екрані було б сміття: досить помилитися з
форматом пікселів чи візуалом, і ніхто б цього не помітив.

## Збірка

Крос-компіляція під Windows з Linux через mingw-w64 у Docker — той самий підхід,
що й для Linux-версії програми. Windows SDK і Visual Studio не потрібні.

```powershell
cd native
.\build.ps1            # обидві розрядності → native\dist\
.\build.ps1 -Clean    # перебудувати образ з нуля
```

На виході: `overlay-{x64,x86}.dll`, `injector-{x64,x86}.exe`,
`hominka-vklayer-{x64,x86}.dll`, `hominka-dcomp-x64.exe`, `hominka-render-x64.exe`
(+ `hominka-render.debug.exe` із символами) і `testhost-*-x64.exe`
(ігри-макети для перевірки).

Сторонні бібліотеки рендера (litehtml, libwebp, nanosvg, imgui, nlohmann/json)
збираються окремим шаром образу за ЗАКРІПЛЕНИМИ комітами — див.
`thirdparty.sh`. Правка нашого коду їх не перезбирає.

Збираються вони й ПІДКЛЮЧАЮТЬСЯ інакше, ніж наш код, і це навмисно. Наше йде з
`-Wall -Wextra`, чуже — з `-w`, а заголовки підключаються через `-isystem`
замість `-I`. Причина проста: чужий код під наші мірки не писався, і GCC 12
видає на ньому десяток хибних попереджень (ImGui — «array subscript is outside
array bounds», бо не бачить `IM_ASSERT` на межі індексу; nanosvg порівнює
`size_t` з `long`). Доки вони сипалися разом із нашими, побачити СВОЄ
попередження в цьому потоці було неможливо. Зараз збірка мовчить — і будь-яке
попередження в ній означає, що воно наше. Джерела компілюються ПІД ЧАС `docker build`, а бінарі
витягуються з образу через `docker cp` — жодного bind-mount: він на Windows
віддає файли з затримкою кешу, і збірка тихо брала вчорашній код (на цьому вже
згоріли — тому так).

## Межі й чесність (виноситься в інтерфейс на кроці 2)

- Функція — **для одиночних ігор**. У змагальних із античитами інʼєкція може
  коштувати бану, і guard туди не пускає взагалі.
- Discord і OBS живуть у білих списках античитів за домовленістю з їхніми
  розробниками; у нас такого списку немає.
- Непідписана DLL + `CreateRemoteThread` — привід для Defender/SmartScreen
  насторожитися. Підпис коду (OV-сертифікат) — окреме рішення й окремі гроші.
- Канал випуску — лише бета/дев, ніколи не stable: активні стрімери не мають
  отримати експеримент замість робочого чату.
